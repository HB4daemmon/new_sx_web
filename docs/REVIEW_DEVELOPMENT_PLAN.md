## 3. 交付目标

本轮不以提高通关率为首要验收目标，而以以下结果验收：

1. 创建角色时，玩家能够说出所选族裔、出身、命格的玩法倾向及至少一项取舍。
2. 选择奖励时，玩家能指出“谁提供输入、什么条件尚未满足、换掉哪件会失去什么”。
3. 战斗结束时，玩家不展开详录就能看到主要输出/保护来源、未触发组件和主要生命损耗。
4. 人物承诺改变实际资源支出、选路或事件选择，不只是改变对白。
5. 玩家可以追踪一个已知人物，并据此选择有可能推进因缘的路线，但不会提前获知尚未抽取的事件。

建议真人验证使用5名未接触当前版本的玩家作为第一轮定性检查：

- 至少4人能正确解释一次奖励选择及其所需输入。
- 至少4人能从结算识别一件未触发组件，并提出一项可行调整。
- 至少4人能理解所接人物承诺的代价、完成条件及是否已完成。

这是小样本可用性门槛，不是胜率或留存的统计结论。第一幕形成有效组合使用现有组件验证，不通过前置命器来满足目标。

## 6. A2：战策与命器的行为摘要

### 6.1 卡面结构

普通组件保留现有结构；战策和命器增加明确的“效果/行为”分区：

- **效果**：保留现有精确效果行，避免本轮把已经可读的规则信息删除。
- **行为**：新增定性摘要，说明行动倾向、成立条件、转换方向和是否额外消耗。

示例：

- 不动如山：“平时以普攻蓄势，伤势较重时优先施展可用怒技；怒技可用而条件未成熟时会短暂保留，随后释放。”
- 怒海：“怒技可用时优先施展，施展后返还怒气并追加伤害。”
- 混元金斗：“实际回复生命后，再获得护盾；满血时没有实际回复，不能带动这条转换。”
- 番天印：“获得护盾时追加伤害；转换本身不扣除刚获得的护盾。”

不要将 `defaultAction: basic` 描述为“永不放怒技”，也不要把满足伤势条件描述为无视怒气和冷却。

### 6.2 实现

- 新增 `abilityBehaviorSummary()`，读取 `defaultAction`、`strategyRules`、`relicConversions`，使用定性条件模板。
- 方向、目标和资源名称使用中文映射，不直接显示 `shield_gain`、`damage_taken` 等内部枚举。
- 战策的规则顺序按配置保留；不存在规则时说明默认行动，不能编造条件。
- 定性模板无法准确概括的规则，使用经过校验的 authored 文案，不退回带数值的 `conditionText()`。
- 保留 `abilityLines()` 的数值职责；卡面、详情、奖励、商店复用相同的行为摘要。
- 在命器既有精确详情中翻译内部枚举；不借此新增转换规则或改倍率。
- 替换提示中的“失去怒气返还、怒技追伤”等事实由 A3 的虚拟装备比较生成，不从标签猜测。

### 6.3 验收

- 当前10种战策和8件命器全部覆盖；无规则遗漏、英文内部枚举泄漏或相互矛盾的说明。
- 同件能力在奖励页、命盘和详情中行为一致。
- 行为摘要不新增具体数值；原有不同阶数的精确效果继续正确显示。
- 所有展示调用不改变 RunState、RNG 和行动日志。

## 7. A3：基于真实来源的适配分析

### 7.1 与奖励评分隔离

新增纯派生分析模块，建议 `src/build-analysis.ts`：

```ts
collectBuildSources(content, state)
analyzeAbilityFit(content, state, candidate, placement)
compareLoadouts(content, state, incoming, targetSlot)
```

本轮不修改 `abilityRole()` 的 `fit/role` 返回规则，不改变 `rollAbilities()` 的 lane、候选顺序或权重。旧评分仅供现有抽取与模拟使用；玩家可见的“已接通”判断改用新分析，不能同时保留相互矛盾的旧 reason。

不建设通用图引擎。只覆盖当前配置中的效果、触发、条件、行动和命器转换；遇到不支持的条件返回“尚不能确认”，不能默认满足。

### 7.2 来源与依赖模型

每条规则至少区分：

| 字段 | 含义 |
| --- | --- |
| source | 装备/槽位/阶数、族裔、出身、命格、已选天赋、基础规则 |
| event | 何种事件触发，以及事件来源所需的机制标签 |
| produces | 真正产生的资源、状态或效果及其目标 |
| reads | 读取的资源、状态、生命条件与门槛 |
| consumes | 实际扣除的资源或状态 |
| gates | 触发机会、条件、概率、频次限制和战策可用性 |

具体要求：

- `apply_status` 是状态来源；`consume_status`、`resource_damage` 和条件声明不是。
- 区分玩家/敌人持有的状态，不能把自身燃烧当成敌方燃烧来源。
- 纳入出身入战效果、族裔、当前命格、已选天赋；未选天赋不算。
- 纳入普攻积怒、受击积怒等基础规则；不能得出“没有回怒装备就没有怒气”的结论。
- `requiresTags/anyTags/excludeTags` 检查的是触发事件的来源，不能检查全身装备有没有某个标签就算接通。
- 环形依赖没有外部起点时不能自证成立；考虑命器转换的 `converted` 防递归限制。
- 只根据实际可执行的动作和已具备的来源建立潜在连接，不把“拥有某个能力”当成每轮一定执行。

### 7.3 输出状态与示例

输出结构包含 `status`、具体来源、缺失项、条件、消耗和不确定性，不输出单一“适配百分比”。

| 状态 | 展示原则 |
| --- | --- |
| 缺少输入 | 当前构筑没有所需来源；指出缺的是什么 |
| 已有潜在来源 | 列出具体名称，但保留门槛、时机和概率条件 |
| 可独立提供效果 | 不依赖额外构筑输入；仍不保证每场都有收益 |
| 尚不能确认 | 外部条件或当前分析不支持；不夸大为可启动 |

以焚心为固定回归样例：

1. 没有敌方燃烧来源：“当前缺少燃烧来源；焚心需要敌方燃烧至少5层。”
2. 只有精怪入战燃烧：“山泽灵性提供入战燃烧，但这一个来源不足以达到焚心门槛。”
3. 存在可持续叠燃烧的装备：“可由〔具体装备〕提供燃烧；是否达到门槛，仍取决于叠层、衰减和战斗长度。”
4. 只有燃烧消耗件：“缺少燃烧来源”，不能把两个消耗件判为相互启动。

规则有明确可证明的上限时可以说明不足；其他情况只说明潜在来源，不静态承诺“必触发”。精怪的入战燃烧与持续叠层必须区别呈现。

### 7.4 替换、升阶与满槽

- 普攻、怒技、战策、命器按唯一槽位，先移除旧件，再分析放入新件后的构筑。
- 组件有空位时按放入空位分析；满槽且未选替换位时，明确“收益取决于替换哪件”，不把将被替换的组件当作可靠来源。
- 选定替换位后比较完整的前后状态，列出“新增来源/失去来源/仍有其他来源/改变行动偏好”。
- 同名奖励按升阶预览，不视为新增来源，不增加虚假触发次数。
- 输出优先展示影响明确的一至两项，剩余内容可展开，避免恢复成构筑调试面板。
- “怒海换为不动如山”必须列出失去怒技返怒和追伤，以及新增防御性行为，不能只显示标签差异。

### 7.5 验收

覆盖缺少来源、来源目标错误、仅消耗无产生、条件生产者、无起点循环、族裔/命格/天赋来源、受战策限制的来源、满槽替换和升阶。所有分析前后 RunState 深相等。

建立固定奖励/商店指纹，证明新解释不会改变候选和 RNG。新分析模块必须加入构建拼接顺序和单文件离线版。

## 8. A4：战斗观测与结算解释

### 8.1 新增观测，不重算战斗

建议新增可选的 `Battle.diagnostics`，包含独立 `schemaVersion`。保持原有 `frames`、`summary` 及战斗计算结果不变。

内容按来源和规则索引聚合，不为每次失败触发追加 replay frame：

- 入战来源清单：全部已装备能力、族裔、出身、命格、已选天赋。
- 每条触发规则的机会数、成功次数、第一阻塞原因计数。
- 在检查时读取到的资源值，例如“焚心检查时燃烧最高值”，不是任意时刻的全场峰值。
- 实际产出、实际消耗、产生了事件但净收益为零的次数。
- 主行动使用次数、战策行动选择记录和命器转换次数。
- 按敌方攻击/持续伤害/自损/系统失败及回合汇总的实际生命损失。
- 有直接事件因果证据的联动对及其成功次数。

来源键须区分 actor、能力 ID、触发器/转换索引。同一技能同时出现在敌我双方时不能串账。命格的显示名解析使用真实命格 ID，不能把来源展示成泛称。

### 8.2 观测插入点和约束

| 插入点 | 观测内容 | 不允许的变化 |
| --- | --- | --- |
| `trigger()` | 事件到达、标签门槛、条件、次数限制、概率结果、成功触发 | 改短路顺序、重抽概率、提前消费 quota |
| `chooseAction()` | 实际选中的动作与战策理由 | 重新评分或改变保留怒技规则 |
| `apply()` | 实际治疗、护盾、怒气、状态增减及零净收益 | 改效果执行顺序和上限 |
| `runRelicConversion()` | 输入事件、转换输出、防递归/取整导致的无输出 | 改转换链深度、`converted` 或 visited |
| `hurt()` / 状态结算 | 真实生命损失、护盾吸收、攻击类别和回合 | 修改伤害公式、将吸收算成掉血 |

实施注意事项：

- 复用已经发生的条件判断和概率结果。记录首次实际阻塞原因，不为了“完整解释”重新执行所有条件。
- 只有执行到了概率判定才记录概率未中；被更早条件拦截不能记为概率失败。
- 实际生命损失使用扣血前后差值，不能把溢出伤害记为真实损耗。保留旧字段，以新增观测修正解释口径。
- 超时导致的失败单独解释，不把系统清零生命归因给最后一次敌方攻击。
- 治疗为零不触发恢复联动；“发动过但没有实际回复”与“从未发动”分开。
- 聚合大小按来源和规则数量有界，不存储所有触发尝试历史。新存档仍应低于现有4MB加载上限，并验证复杂长战斗。
- 不增加战斗规则可读取的诊断状态，不让观测反过来影响执行。

### 8.3 零触发分类

“没有 contribution”不能直接等同于“没有生效”：

| 情况 | 结算说明 |
| --- | --- |
| 触发型组件未触发 | 显示零次，以及已观测的首要阻塞原因 |
| 触发事件没有发生 | “本场未出现〔闪避/实际回复等〕” |
| 资源阈值未到 | “检查时最高〔观测值〕，需要〔门槛〕” |
| 战斗在对应时点前结束 | “未到回合结束/胜利后等触发时点” |
| 效果执行过但净收益为零 | “已发动，但怒气已满/无实际回复”等有证据的说明 |
| 纯属性组件 | “属性加成已计入”，不列作未触发 |
| 战策改变了动作但无额外产出 | 单列行动影响，不能判作无效组件 |
| 旧战斗没有诊断 | 显示已有贡献，缺失部分标为“旧战报未记录” |

全量明细必须包含所有入战组件；默认摘要只选最重要的未生效项，但提供展开入口。

### 8.4 默认结算

在播放结束或玩家跳过后、进入下一页面前，默认显示三条事实：

1. **本场关键**：主要输出来源，或实际回复/提供护盾的来源及观测量。
2. **未生效**：零触发来源和确认到的原因；没有未触发项时如实说明。
3. **主要损耗**：哪类敌方攻击或持续伤害造成最多实际掉血，集中在哪些回合。

不要使用现有混合加权分数直接宣称某件装备“决定胜负”。提供护盾不等于这件装备实际吸收了同量伤害；本轮不引入共享护盾的任意分摊规则。

诊断虽在开战时已产生，但不能在回放尚未结束时泄露最终伤害、死因或结局。集中定义结算可见性判断，以 `cursor === frames.length - 1` 为门槛；所有最终聚合字段复用它，不能只给主摘要加判断而从明细/提示泄露。败战同样显示摘要，点击“回望此生”后仍可查阅本次记录；不扩展为跨局保存。

### 8.5 “组合接上了”的闭环

- 获取或替换后，显示由 A3 证明的具体潜在关系，例如“反震的反击可为鳞纹杯提供触发事件”。
- 下一场结算显示该组件实际触发次数；有直接事件来源证据时，显示该联动对触发次数。
- 对燃烧等共享状态，只列出已知来源集合和消费者次数。没有状态逐层来源证据时，不声称某装备独自促成了某次焚心。
- 不把“同时出现过”当成因果，也不为做到精确归因而新增整套资源溯源账本。
- 提示可由现有行动日志和当前构筑派生，不新增跨局记录或额外随机状态。

## 9. B1：有限的人物承诺状态

### 9.1 状态与内容

引入仅服务本轮四种承诺的结构，不建设可配置任意任务的 DSL。

```ts
type PromiseStatus = 'active' | 'fulfilled' | 'broken' | 'expired' | 'declined';

interface CharacterPromiseState {
  definitionId: string;
  status: PromiseStatus;
  acceptedAt?: { act: number; row: number; nodeId: string };
  bypassPermit?: {
    state: 'available' | 'consumed' | 'expired';
    issuedAtNodeId: string;
    usedAtNodeId?: string;
  };
  evidenceNodeId?: string;
  finalRewardOffered: boolean;
  settlementClaimed: boolean;
  reason?: string;
}
```

建议 `RunState` 新增：

- `promises: Record<string, CharacterPromiseState>`。
- `trackedCharacter?: string`，保存人物 `relationKey`。

当前工作区已统一为 `trackedCharacter` / `trackCharacter(relationKey | null)`：设置、切换和取消都会进入 `actionLog`，不消费 RNG；`followCharacter(string)` 与 `clearCharacterFollow()` 保留为旧命令兼容层。载入时会把唯一的旧 `followedCharacter` 迁移到 canonical 字段，删除旧字段，并拒绝 canonical/legacy 冲突；对应存档、取消和重放回归已通过。

内容增加有限的 `characterPromises` 注册表，类型仅为“保留灵石、完成精英、借道绕行、救助敌方”。门槛、期限、允许节点、兑现效果和对应人物都写在配置中，不在引擎硬编码人物 ID。期限使用明确的幕/行和结算边界；绕行资格的期限来自该定义，不额外存一份可漂移的规则值。

新世界效果可命名为 `start_promise / fulfill_promise / abandon_promise`，必要条件为 `promise_state`，支持匹配一个或多个明确状态以及“尚未接受”；终段奖励另用 `promise_reward_available` 检查。实现前锁定命名和参数，同步扩展类型、校验、条件显示、选择可见性和测试。`fulfill_promise` 必须核验对应任务类型的真实证据，不能成为任意事件直接写 kept 的新捷径。

### 9.2 状态机和权威来源

- 未接受时没有记录；接受后进入 active。
- 只有对应真实动作完成，才能进入 fulfilled。
- 违背承诺进入 broken；错过期限进入 expired；明确拒绝或放弃进入 declined。
- 同一人物承诺不能重复接受以刷奖励；已兑现不能再次领奖。
- 终段选择借命器时，在同一事务中将 `finalRewardOffered` 标记为 true，再走既有获得/待替换流程。重复事件不能再次发放；取消待替换视为放弃这次赠物，不清除标记。不能只依赖 `maxPerRun`，因为当前事件池耗尽时存在回退到基础池的行为。
- “帮忙”与“立约”分开，不能继续沿用帮忙后无论如何都自动标记 promise 的行为。
- `promises` 是新状态的权威来源；保留 `met_* / *_promise / *_kept` 作为已有内容的兼容投影，由专用处理函数同步，不能让旧事件分支直接设置 kept 绕过验收。
- 追踪与承诺独立：可以同时承担多个不同人物的承诺，但最多追踪一人。取消追踪不撤销承诺。
- 所有进度在动作正式提交时结算。不得在渲染、回放进度、静态预览或读取存档时推进。
- `storyLog` 记录立约、违约、兑现及证据节点；追踪操作本身只进 `actionLog`，不伪造剧情。

### 9.3 立约入口和旧分支改造清单

| 人物 | 相识与接受时点 | 完成时点 | 截止/未接受处理 |
| --- | --- | --- | --- |
| 姜子牙 | 首遇相识后，独立选择接受保留军粮钱 | 中段交付，且历史上没有违约 | 第三幕结束前；未接受不能在中段补签并倒算历史 |
| 雷震子 | 首遇相识后，独立选择接受危险任务 | 接受后的正式精英胜利结算 | 第二幕结束前；过去已获胜的精英不倒算 |
| 土行孙 | 首遇仅相识，中段明确接受护送借道才立约并发资格 | 实际使用借道 | 最迟第四幕最后一个普通战斗行结算后 |
| 云霄 | 首遇仅相识，中段救助选项当场接受并履行 | 实际支付救助代价、完成救助的同一事件事务 | 不接受则不记践约；不制造虚假的跨幕等待任务 |

配置改造必须显式覆盖：

- 移除四条首遇 `help` 和检定成功分支直接写入的 `*_promise`。
- 姜子牙/雷震子增加明确的接受/拒绝阶段；土行孙/云霄不在首遇自动立约。
- 现有 `promise.keep/leave` 本质是是否收取普通赠物，不是是否践约。将其文案/阶段明确为赠物选择；若保留赠物，维持单次上限且与任务完成奖励分开，不将它算成践约证据。
- 替换四条中段旧 `keep/risk` 的直接写 kept 效果，包括 `check.success`，不是只改选项标题。未选择新任务的玩家仍有叙事/即时收益分支，但没有同一践约事实。
- 姜子牙/雷震子中段根据未接受、活跃、已完成、违约/过期分别提供合法选择；拒绝后不能反复接受刷奖励。
- 土行孙终段在任务仍活跃、资格可用时暂不进入随机候选，避免尚能完成任务却提前消费唯一终段事件。未接受、拒绝、过期仍允许告别分支，已完成允许借命器。
- `fulfilled + consumed`、`expired + expired` 等组合必须一致；非绕行任务不能带绕行资格。保存、载入、重放都验证这套不变量。

### 9.4 动作提交与幂等

在 `Game` 增加唯一的内部提交后结算函数，例如 `settlePromisesAfterAction(context)`。由实际公共动作方法在成功完成状态修改后调用，不依赖 UI 和 `command()` 单独包装。

| 操作 | 检查承诺的时机 |
| --- | --- |
| `chooseEvent()` | 本次选择的全部效果、任务变更和即时授予处理结束后；使用最终余额 |
| 无需替换的购买、回复/属性商品、刷新 | 实际扣款并完成交易后 |
| 需要替换的购买 | `buy()` 创建 pending 时不视为已支出；在 `replace()` 完成实际扣款后检查 |
| `cancelReplacement()` | 不扣款，不改变保留承诺 |
| `finishBattle()` | 正式接受战斗结果后判定精英证据，只兑现一次 |
| 绕行、离开节点及跨幕 | 使用资格/推进进度完成后核查证据与期限 |

内部的 `applyWorld()`、`acquire()`、`completeAcquire()`、`advance()` 不重复调用这层结算，避免一个公共动作多次兑现。姜子牙交付先核验历史与余额，在同一提交中标记兑现并扣款，不被最终检查误判为违约。

失败的合法性检查不写行动日志或任务进度。现有命令名保持原样，新任务结果由命令确定性派生；不要为同一兑现再追加一条会被重放执行第二次的隐式命令。所有任务奖励经相同的幂等守卫处理，若派生奖励产生天赋选择或待替换，保留原事务的后续流程。

## 10. B2：四条人物线的实际取舍

### 10.1 姜子牙：保留军粮钱，影响购买计划

涉及 `character.ziya.1/.2/.3`。

- 首遇的立约选择明确约定：在交付前持续保留一笔灵石。
- 第一版保留额度沿用原中段付款的18灵石，配置化；不是本轮额外加价。
- 接受时余额不足则不能立约，但保留不承担承诺的合法选项。
- 活跃期间可以自由购买或支付，不硬锁灵石；已提交的支出使余额低于保留额时记为违约，之后补回不能抹去历史。
- 商店购买、刷新、事件付款都提前显示对该承诺的影响。未确认替换或取消购买不算实际支出。
- 中段见面时，持续保留成功才可交付并记为 kept；交付是兑现事务，不应因交付款本身触发违约。
- 不允许原 `risk` 的一次检定绕过整个保留过程直接写 kept。可保留其他叙事/即时收益，但必须与践约区分。
- 不改最终 `myth.whip` 的阶段与获取槽位。

验收：边界余额、连续多次购买、事件扣款、取消替换、违约后补回、交付、重复交付、未再见到人物而过期。

工程上需要审计全部 gold 写入入口：`completeAcquire()`、`buy()`、`refresh()`、`applyWorld()` 等。按一次已提交动作的最终余额核查，避免同一事务中的中间值误判；不能只在 `Game.command()` 包装，因为 UI 也会直接调用具体方法。

### 10.2 雷震子：选择现有精英路线并完成目标

涉及 `character.leizhenzi.1/.2/.3`。

- 首遇立约时开始任务：承诺之后、第二幕结束之前完成一场现有精英战。
- 开始前确认期限内仍存在可达精英；不把已打过的精英计入。
- 使用现有节点、敌人和战斗目标，不增加事件内额外战斗，不插入节点，不调整精英强度。
- 只有 `finishBattle()` 正式结算且 `won === true` 才兑现；生存/破阵目标完成同样有效，不要求击杀。
- 中段见面时分别回应“已完成、仍可完成、已错过”，不再付款或检定就直接兑现。
- 任务中段收益至多发放一次；如果精英胜利导致境界突破，天赋队列与普通奖励仍按现有规则处理。
- 失败死亡不记完成；选择其他路线直到截止则过期，不追加惩罚战。
- 后期 `myth.wings` 仍要求真实践约，不提前发放。

验收：首遇晚于本幕精英、跨幕完成、目标型精英、既往战斗不倒算、未播放完不兑现、读档重放不重复、错过期限。

### 10.3 土行孙：真实绕行，放弃对应战斗全部收益

涉及 `character.tuxingsun.1/.2/.3`，以及限定的路线动作。

- 中段提供一次“借地道护送”的机会。选择后获得仅本局、仅该任务使用的绕行资格。
- 资格只能用于当前可达的普通战斗节点，不能跳过精英、Boss、重大事件或其他幕的任意节点。
- 增加 `bypassCombat(nodeId)` 命令。验证资格与 `available()` 后，正常记录所经节点，标记借道证据，再且仅再 `advance()` 一次。
- 不调用 `simulateBattle()`；不生成奖励候选；不发该战灵石、修为、装备或战斗胜利奖励。
- 真实收益是避免该战伤势，真实代价是放弃该战全部成长机会。不是先打完再“舍弃卡牌”。
- 没有使用借道前不能设置 kept；使用后才兑现护送承诺，最终 `myth.earth` 阶段不变。
- 资格可延续到第四幕的普通战斗，截止于该幕最后一个普通战斗行结算后。当前模板对应零基 `act: 3, row: 5`；值写入任务配置并校验，不在引擎按人物硬编码。接受时校验期限内尚有未来可达普通战斗，不能发不可用的资格。
- 玩家不使用时普通 `enter()` 完全不变；借道是任务专属附加动作，不弹出通用战前预览。
- 已走节点计数仍是40步上限；借道节点必须标为“绕行”，不能伪装为已获胜战斗。
- 资格发放时写 `available`；成功借道在同一提交中改为 `consumed`、写证据节点并兑现；过期改为 `expired`。不得根据当前页按钮是否还显示来判断资格是否消耗。

验收：绕行前后生命不因战斗变化、零战斗 RNG/奖励抽样、零该战收入、行数只前进一步、资格只消耗一次、不可越级/跨 lane、不能绕 Boss。

### 10.4 云霄：救助对立阵营，留下跨人物回响

涉及 `character.yunxiao.1/.2/.3`，最小扩展一个杨戬后续事件 `event.3.ruins`。

- 中段让玩家明确选择是否救助一名阐教伤者；这是云霄践约的实际行动。
- 救助支付明确的当下代价，第一版复用现有事件代价量级，不叠加永久属性奖励来掩盖取舍。
- 该选择在同一事件动作中接受并完成救助承诺；首遇是否收下普通赠物不构成前提。支付条件不足时不能选择，保留不支付的合法分支。
- 成功救助设置 `yunxiao_kept` 和独立事实，例如 `yunxiao_saved_chan_envoy`。
- 不救助保留合理的即时收益或保全自身分支，但不获得救助事实和同一践约奖励。
- 现有“赵公明救粮旧事”保留为可信度/救助方式的特殊解法，不能只亮出旧事就凭空完成救助。
- 杨戬线读取此事实，提供跨阵营承认或援手。不要自动抹掉玩家原先“同道/分道”等立场。
- 尚未与杨戬相识时，只保存事件事实，不提前把他加入已知人物追踪列表。

建议具体回响：

将 `event.3.ruins` 保留为同一个事件，原四选项放入 `root`；新增只有救助事实满足时进入的 `mercy` 阶段，提供“接受这份援手”和“仍按原先立场交谈”两项。前者形成明确的人物关系结果，后者进入原 root。

这样不新增人物/事件、不覆盖原四条结局选择，并遵守现有每阶段2至4项、最多5阶段的限制。不得直接给已满四项的阶段塞第五项。

验收：救与不救的后续不同；未相识不泄露人物；旧阵营事实保留；赵公明特殊解法确实完成救助；每条新分支有独立事后文案和合法退出。

## 11. B3：单条主动追踪与可行动线索

### 11.1 追踪行为

- 因缘页只允许追踪已经实际相遇的人物。新增共用纯函数 `knownCharacters()`，通过人物注册信息中的明确相识事实、或已经进入的该人物本人出场场景判定，不能因为未来配置中有 relationKey 或单独一条 thread 就可追踪。
- 进入本人出场场景、已呈现相见叙事就算相识，不要求必须选择帮忙；另一个人物提及其名字、跨线留下待回响事实不算。因缘列表、追踪命令和线索都复用此口径。
- 目标接口为 `trackCharacter(relationKey | null)`，作为正式动作进入 `actionLog` 和 `command()`；校验人物 ID、已知状态和操作阶段。当前实现仍为 `followCharacter(string)`，取消通过独立的 `clearCharacterFollow()` 完成，需在发布前统一或明确兼容层。
- 只允许在地图、没有待处理天赋或换装事务时改变追踪；其他阶段可查看，但不能让追踪改写正在处理的事件。
- 设置/切换追踪本身不调用 RNG；切换后生效于下一次尚未解析的事件。
- 取消只移除追踪，不取消承诺、不清除相识和既往故事。
- 默认不自动追踪，不让首次对话偷偷改变抽取概率。

### 11.2 线索必须能帮助选路

不能只增加一个收藏图标。地图显示一条当前人物线索，并为符合条件的现有事件路线加轻量标记：

- 根据已知事实、当前幕、既有承诺以及可达路线，指出“前方奇遇可能有粮册消息”等地点/节点类型线索。
- 活跃的雷震子任务可标出现有精英方向；土行孙显示是否存在可借道的普通战斗。
- 不展示具体未抽取事件 ID、事件标题、选项、神话奖励或隐藏事件身份。
- 本幕没有机会时显示等待/错过，不把所有人物永远标成“前方可遇”。
- 线索是机会，不是保证。UI 文案必须使用“可能”“传来消息”等准确措辞。
- 不绘制不可达路线的引导，不更改节点类型、位置或 lane 连接。

### 11.3 与事件选择的一致性

- 从 `resolveStory()` 中抽出纯候选筛选函数，共用 requirements、幕次、hiddenOnly、出现次数和既有 fallback 规则。
- 线索只读候选，不调用 weighted/random，不写 `node.ref`、`seenEvents` 或未来 eventPhase。
- 只对尚未解析且符合条件的普通事件候选给予追踪增权。建议首版乘数为2，作为配置参数，叠加原有前因权重。
- 增权不突破资格、出现次数规则，也不影响隐藏池、固定重大事件、奖励和战斗随机流。
- 已解析的节点仍用既有 `ref`，反复切换追踪不能重抽同一个事件。
- 无追踪时，候选顺序、权重和 RNG 调用与重构前一致。
- 参数2是开发初值，不是已经验证的平衡结论；用配对种子检查实际遇见率与其他事件挤出情况后再定。

### 11.4 验收

未相识不能追踪；设置、切换、取消可以存取和重放；只查看线索时完整状态不变；合法事件机会才显示线索；同一事件不因读档和追踪切换重抽。

- A新增诊断字段为可选且有版本，旧战斗只做展示降级；不得自动重放以补字段。
- B已使用新的内容/规则版本 `4.4.0`、UI `18.0` 和存档键 `fengshen-run-v44`；保留 `v43/v42/v4/v1` 等现有旧档的读取/导出能力。
- 不覆盖、删除或静默迁移旧局；旧档不能按4.4规则续跑这一点必须在重开/导入位置说明。
- 新字段校验需覆盖状态枚举、配置引用、证据节点、资格是否已消费及诊断大小；拒绝损坏状态，不让未知任务 ID 进入运行。
- B测试集全部通过后再把新版本合入部署分支。回退到4.3时保留4.4存档原文，不强行载入旧引擎。

### 16.2 主要风险

| 风险 | 处理方式 |
| --- | --- |
| 说明修复暗改掉落 | 新分析与旧评分分离，固定奖励/商店指纹 |
| 为解释概率而多抽一次随机 | 只记录实际判定，逐流比较 RNG |
| 消耗件自证来源、循环自启 | 产生/读取/消耗分开，根来源与方向校验 |
| 零贡献被误报为无用 | 区分纯属性、动作影响、触发失败、零净收益 |
| 诊断体积超过存档限制 | 规则级聚合，不记录全量失败帧，最坏场景测量 |
| 人物承诺只有文案变化 | 用资源余额、正式精英结算、实际绕行和跨线分支验收 |
| 任务因出现过晚而不可能完成 | 接受前可达性检查，明确期限，保留拒绝与过期路径 |
| 追踪变成预抽/必遇 | 纯候选提示、仅增权、已解析事件不重抽 |
| 云霄回响覆盖其他人物选择 | 独立事实和新回应阶段，保留原阵营/关系结果 |
| 为调平衡越界 | 仅核查新增人物经济，不改Boss/路线模板/原策略 |

### 16.3 本轮完成定义

第1、2、5项均有可用功能、正反路径测试和存档/重放验证；第1、2项另有当前离线包的通用 Node 浏览器验收，第5项的人物专用 UI 流程仍待补验。第3、4、6项及备用槽等旁支没有混入。报告明确区分自动测试、场景夹具、固定策略模拟和真人观察。

截至本计划日期，代码级完成定义满足：第1、2、5项已有实现、自动回归、存档/重放验证和 Node 浏览器验收记录；第3、4、6项及备用槽等旁支没有混入。真人任务和与旧基线的逐种子对照仍未完成，因此本次提交应称为“实现、自动验证和离线浏览器验收完成”，不能描述为真人验收完成或线上发布完成。

任何未完成的阻塞原因、来源类型或人物分支应作为未完成项列出，不能用“核心体验已优化”代替可检验的完成结论。
